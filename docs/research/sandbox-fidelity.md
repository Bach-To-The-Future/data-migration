# Sandbox fidelity: can a SQL Server container and local PySpark stand in for the real platforms?

Research for issue #4. Sources read on 2026-10-13. Documentation only: no container image was pulled and nothing was run, so every statement about what "works" is what the vendor documents, not something observed here.

## Answer

**Yes for the source side, with configuration. Partly for the target side.**

- **SQL Server in a Linux container is a faithful stand-in for the artefact types v1 converts** (query batches, stored procedures, views, functions, triggers). Microsoft states that SQL Server on Linux, including containers, uses the same Database Engine as on Windows, and the Developer editions are free for development and test. What the container lacks is almost entirely outside the T-SQL engine (SSIS, Agent subsystems, unsafe CLR, extended stored procedures, FILESTREAM, non-SQL-Server linked servers). An artefact that touches one of those cannot be run in the sandbox and must be reported as not reconcilable rather than as failed.
- **Local PySpark with open-source Delta Lake is a faithful stand-in for DataFrame query semantics only if it is pinned and configured to mirror the target runtime.** Out of the box it differs from Databricks in ways that let code reconcile locally and still behave differently on Databricks: Spark Classic versus Spark Connect, session time zone, JDK, and (for targets older than Databricks Runtime 17.0) ANSI mode. Those four can be closed locally.
- **Some Databricks behaviour cannot be reproduced locally at all**: Photon, Databricks' own patches on top of the Apache Spark release, multi-statement transactions, Unity Catalog stored procedures, and more than 200 Databricks-only built-in functions. A conversion that depends on any of these can only be reconciled against a real workspace.

So the sandbox is good enough to be the default reconciliation environment, but "reconciled in the sandbox" is a weaker statement than "reconciled on Databricks", and the tool should say which one it means. The only documented way to close the remaining gap is to run the converted code on real Databricks compute, for which Databricks Connect is the lowest-friction route.

## Gaps that matter for reconciliation

"Dangerous" means the conversion can reconcile locally and still behave differently on the real platform. "Blocking" means it cannot be run in the sandbox at all, which is visible and therefore safer.

### Target side: local PySpark versus Databricks

| # | What differs | Why it matters for reconciliation | Closable locally? |
|---|---|---|---|
| T1 | **Spark, Delta, Python and JDK versions.** Each Databricks Runtime bundles a specific set (table in [Version map](#version-map)). `pip install pyspark` today gives 4.2.0. | A different Spark minor version changes function behaviour and defaults. Dangerous. | **Yes.** Pin `pyspark`, `delta-spark`, Python 3.12 and the JDK to the target runtime. An exact Delta match for Runtime 19 is not available in open source (see T7). |
| T2 | **ANSI mode default.** On by default in Apache Spark 4.0+ and in Databricks Runtime 17.0+ and serverless. Off by default on Runtime 16.4 LTS and below. Databricks SQL warehouses default to `ANSI_MODE = TRUE` only for accounts created on or after 2022-10-19. | With ANSI off, invalid casts and overflows return NULL or wrap instead of raising. A conversion can reconcile under one setting and produce different rows under the other. Dangerous when the customer targets an older runtime or an old account's warehouse. | **Yes.** Set `spark.sql.ansi.enabled` explicitly to the target's value instead of relying on the default. Serverless cannot change `spark.sql.storeAssignmentPolicy`, so keep that at `ANSI` locally. |
| T3 | **Spark Classic versus Spark Connect.** Serverless compute, standard-access-mode clusters and Databricks Connect use Spark Connect. Local PySpark defaults to Spark Classic. | Under Spark Connect, RDD and `SparkContext` APIs are unavailable, analysis errors surface at execution rather than at transformation, and a DataFrame built from a temp view follows the view if it is later replaced. Code that works in a local classic session can fail or change results on serverless. Dangerous. | **Yes, mostly.** Run the local session in Spark Connect mode (`spark.api.mode=connect`, or `spark.remote=local[*]`). Serverless-only limits (128 MB row size, no global temp views) are not reproduced. |
| T4 | **Session defaults.** Open-source `spark.sql.session.timeZone` defaults to the machine's local zone; serverless defaults to `Etc/UTC` and Databricks SQL to UTC. Open-source `spark.sql.sources.default` is `parquet`; Databricks `CREATE TABLE` without `USING` creates Delta. Runtime 18 and above run JDK 21, where float-to-string output and locale data differ from JDK 17. | Timestamp results shift with the zone; string renderings of floats differ by JDK. Dangerous, and the reconciliation comparison itself can report false differences. | **Yes.** Set the time zone to UTC, always write `format("delta")`, run the JDK major version of the target runtime. |
| T5 | **Photon.** A native C++ engine that replaces Spark execution on serverless and SQL warehouses, and is on by default for classic compute created in the UI. Not available outside Databricks. | The engine that produces the production result is not the engine that produced the reconciled result. Databricks documents Photon as API-compatible and says queries "still produce correct results"; it documents no semantic differences. | **No.** Only a run on Databricks exercises Photon. Residual risk is undocumented rather than known. |
| T6 | **Databricks' patches to Spark.** Each runtime "includes Apache Spark x.y.z" plus Databricks' own fixes and behavioural changes, shipped as dated updates under the same version number. | Release notes for Runtime 18 LTS and 19 list changes that alter query results (for example `NATURAL JOIN` case-insensitive matching, `LEFT OUTER JOIN LATERAL` row-dropping fix, `HAVING` evaluated before window functions with generators). The open-source release of the same number may or may not have them. Dangerous but rare. | **No.** Not reproducible; mitigated only by running on the target runtime. |
| T7 | **Delta Lake features.** `MERGE` (including `WHEN NOT MATCHED BY SOURCE`), `CHECK` and `NOT NULL` constraints, generated columns and identity columns all exist in open-source Delta. Identity columns in SQL DDL arrived only in Delta 4.4.0; before that only the `DeltaTable` builder API. Primary key, foreign key and unique constraints are Databricks informational constraints; open-source Delta documents only `NOT NULL` and `CHECK`. | DML conversions can be reconciled locally. Identity values are documented on both sides as unique but not contiguous, so they must never be compared with SQL Server `IDENTITY` values. `MERGE` duplicate-match detection changed in Runtime 16.0. | **Yes for `MERGE`, `CHECK`, `NOT NULL`, identity.** Use `delta-spark` 4.4+ if the conversion emits identity DDL. Informational key constraints are not enforced on Databricks either, so they do not affect results. |
| T8 | **Multi-statement transactions.** Databricks supports `BEGIN ATOMIC ... END` and `BEGIN TRANSACTION ... COMMIT/ROLLBACK`, but only when every written table is a Unity Catalog managed table with catalog commits, on Runtime 18.0+ or a SQL warehouse; interactive transactions only on SQL warehouses. Apache Spark 4.2 and open-source Delta document no equivalent. | A stored procedure whose correctness depends on rollback cannot be reconciled locally: each local statement commits on its own. Blocking for the rollback path; dangerous if only the happy path is reconciled and reported as fully reconciled. | **No.** |
| T9 | **Stored procedures and SQL scripting.** `CREATE PROCEDURE` is Unity Catalog only (Runtime 17.0+). Apache Spark 4.2 documents SQL scripting (compound statements, cursors, handlers) but its SQL syntax reference lists no `CREATE PROCEDURE`. | Only matters if the escape hatch emits SQL procedures; v1's target is DataFrame code. Blocking. | **No** for procedures; **yes** for scripting blocks run inline. |
| T10 | **Unity Catalog three-part names.** Databricks addresses tables as `catalog.schema.table`; Unity Catalog stores object names in lower case. A default local session has only `spark_catalog`. | Generated code that hard-codes a catalog fails locally. Blocking. | **Yes.** Either parameterise the catalog in generated code, or run the open-source Unity Catalog server with its Spark connector, which documents three-part names locally with Delta. The second option adds a service to the sandbox. |
| T11 | **Databricks-only built-in functions.** Comparing Databricks' alphabetical function list with the Apache Spark 4.2.0 function reference gives roughly 218 names on Databricks only: `ai_*`, `h3_*`, most `st_*`, `read_files`, and the T-SQL-flavoured `getdate`, `charindex` and `iff`. | A converter that passes T-SQL `GETDATE()` or `CHARINDEX()` through unchanged would produce code that runs on Databricks and fails locally. Blocking, not dangerous. | **Yes, by construction.** Restrict generated code to functions present in the pinned Apache Spark version, or report the fragment as not reconcilable in the sandbox. |

### Source side: SQL Server container versus production SQL Server

| # | What differs | Why it matters for reconciliation | Closable locally? |
|---|---|---|---|
| S1 | **Version.** Container images exist for SQL Server 2017, 2019, 2022 and 2025 only. The customer's production server may be older or different. | Engine behaviour changes between versions. Dangerous. | **Mostly.** Use the image matching production where one exists. For older sources, set the database compatibility level: SQL Server 2025 accepts levels 100 to 170 and a restored database keeps its level. Compatibility level does not bring back discontinued functionality. |
| S2 | **Server collation.** Set at container creation with `MSSQL_COLLATION`; otherwise a default mapped from the language ID (the documented US English default is `SQL_Latin1_General_CP1_CI_AS`). No Linux-specific collation restriction was found. | Server collation is the default for new databases and governs string columns in `tempdb`, so temp-table comparisons in stored procedures follow it. Dangerous if it differs from production. | **Yes.** Set `MSSQL_COLLATION` to the production server collation when the container is first created. |
| S3 | **Features absent on Linux**: system extended stored procedures (`xp_cmdshell` and others), CLR assemblies with `EXTERNAL_ACCESS` or `UNSAFE`, FileTable and FILESTREAM, linked servers to anything other than SQL Server, distributed queries with third-party connections, merge replication, Windows authentication for linked servers. | An artefact that uses one of these cannot execute in the sandbox. Blocking. | **No.** Detect and report as not reconcilable. |
| S4 | **SQL Server Agent.** Present but disabled by default (`MSSQL_AGENT_ENABLED=true`). T-SQL job steps run; the CmdExec, PowerShell, SSIS, SSAS, SSRS and Queue Reader subsystems and alerts are unsupported. | Agent jobs are a recognised-only artefact type, so nothing needs to run. Relevant only if a later version executes jobs. | **Partly** (T-SQL steps only). |
| S5 | **SSIS.** Installing SSIS in containers is not supported, and SSIS is not available at all for SQL Server 2025 on Linux. | SSIS packages are recognised-only, so nothing needs to run. A later version that reconciles packages would need a Windows host. | **No.** |
| S6 | **Full-Text Search.** A separate package (`mssql-server-fts`) on Linux, with fewer document filters than Windows. Whether the stock image includes it was not established. | Artefacts using `CONTAINS` or `FREETEXT` need it; both sample databases define full-text indexes. Blocking for those artefacts. | **Yes**, by building a custom image that installs the package, if the stock image lacks it. |
| S7 | **Edition.** The container runs whichever edition `MSSQL_PID` names. SQL Server 2025 has two Developer editions: Enterprise Developer (all Enterprise features) and Standard Developer (Standard features). | Enterprise-only features and limits differ from Standard. Rarely affects query results. | **Yes.** Choose the Developer edition that mirrors the customer's production edition. |
| S8 | **Host platform.** Images are supported only on Linux hosts with x86-64 CPUs; emulation (Rosetta 2, QEMU) is untested and unsupported; SQL Server in Windows containers is not covered by support. | Affects who can run the sandbox, not results. An Apple-silicon developer machine is outside the supported configuration. | **N/A.** Microsoft's container pages give Windows examples (PowerShell and cmd command forms, a `C:\SQL` volume path), so running the Linux image from Docker on an x86-64 Windows machine is an expected development setup even though the support statement names Linux hosts. |

- From Runtime 19, Databricks no longer issues minor versions. A version is released, receives features and fixes under the same number for about six months, then becomes LTS for three years ([support lifecycles](https://docs.databricks.com/aws/en/release-notes/runtime/databricks-runtime-ver)). Runtime 18 was the first to use single-page "unified" release notes; 18.0, 18.1 and 18.2 preceded it ([Runtime 18 LTS notes](https://docs.databricks.com/aws/en/release-notes/runtime/18)).
- Serverless compute does not expose a runtime version. It exposes an environment version: environment 6 (2026-09-03) pairs with Databricks Connect 19, environment 5 with 18, environment 4 with 17.3; all use Python 3.12.3 and JDK 17 ([environment versions](https://docs.databricks.com/aws/en/release-notes/serverless/environment-version/)).

What open source offers to match:

- Apache Spark's current releases are 4.2.0 (2026-07-14), 4.1.3 and 4.0.4 (2026-07-15) and 3.5.9 (2026-07-16) ([downloads](https://spark.apache.org/downloads.html), [PyPI](https://pypi.org/project/pyspark/#history)). Spark 4.2 runs on Java 17, 21 or 25 and Python 3.10+, and "runs on both Windows and UNIX-like systems" ([overview](https://spark.apache.org/docs/latest/)).
- Delta Lake's compatibility table lists Delta 4.0.x for Spark 4.0.x, and Delta 4.1.x, 4.2.x and 4.3.x for Spark 4.0.x and 4.1.x ([releases](https://docs.delta.io/latest/releases.html)). Delta 4.4.0 added Spark 4.2 support and is built for Spark 4.2.0, 4.1.0 and 4.0.1; 4.4.1 is current ([GitHub releases](https://github.com/delta-io/delta/releases), [PyPI](https://pypi.org/project/delta-spark/#history)).
- Consequence: Runtime 17.3 LTS maps to `pyspark` 4.0.x with `delta-spark` 4.0.x, and Runtime 18 LTS to `pyspark` 4.1.x with `delta-spark` 4.2.x. Runtime 19 reports Spark 4.2.0 with Delta Lake 4.2.0, a pairing open-source Delta does not publish (Spark 4.2 needs Delta 4.4+), so the nearest local match is `pyspark` 4.2.0 with `delta-spark` 4.4.x. The version labels in a runtime describe Databricks' own build, not an installable open-source combination.
- Local Delta needs explicit session configuration: `spark.sql.extensions=io.delta.sql.DeltaSparkSessionExtension` and `spark.sql.catalog.spark_catalog=org.apache.spark.sql.delta.catalog.DeltaCatalog`, or `configure_spark_with_delta_pip()` ([Delta quick start](https://docs.delta.io/latest/quick-start.html)).

### ANSI mode (T2)

- Apache Spark: "Since Spark 4.0, `spark.sql.ansi.enabled` is on by default" ([SQL migration guide](https://spark.apache.org/docs/latest/sql-migration-guide.html)); with it off, decimals overflow to NULL and other numerics wrap as in Java ([ANSI compliance](https://spark.apache.org/docs/latest/sql-ref-ansi-compliance.html)).
- Databricks Runtime: ANSI mode is "enabled by default in Apache Spark 4.0 and Databricks Runtime 17.0 and above"; `spark.sql.storeAssignmentPolicy` defaults to `ANSI` independently ([ANSI compliance in Databricks Runtime](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-ansi-compliance)).
- Serverless: ANSI mode is on by default; it can be turned off for casts, arithmetic and parsing, but the store assignment policy cannot be changed ([serverless limitations](https://docs.databricks.com/aws/en/compute/serverless/limitations), [serverless migration guide](https://docs.databricks.com/aws/en/compute/serverless/migration)).
- Databricks SQL: `ANSI_MODE` system default is `TRUE` "for accounts created on or after October 19, 2022"; with `FALSE` the warehouse uses Hive-compatible behaviour, for example `1/0` returns NULL and `cast('a' AS INTEGER)` returns NULL ([ANSI_MODE](https://docs.databricks.com/aws/en/sql/language-manual/parameters/ansi_mode)).

### Spark Connect versus Spark Classic (T3)

- Spark Connect is used by Scala notebooks on standard compute from Runtime 13.3, Python notebooks on standard compute from 14.3, serverless compute, and Databricks Connect ([compare Spark Connect to Spark Classic](https://docs.databricks.com/aws/en/spark/connect-vs-classic)).
- Differences Databricks documents: schema analysis is lazy rather than eager, so `spark.sql("select 1 as a, 2 as b").filter("c > 1")` raises only when the plan is sent to the server; temp views are looked up by name at execution, so replacing a view changes DataFrames already built from it; UDFs are serialised at execution rather than creation (same page).
- Serverless: "Only Spark Connect APIs are supported. Spark RDD APIs are not supported"; default session time zone is `Etc/UTC`; `spark.createDataFrame` rows are limited to 128 MB; global temp views are unsupported ([serverless limitations](https://docs.databricks.com/aws/en/compute/serverless/limitations)). Standard access mode also rejects RDD APIs ([standard compute limitations](https://docs.databricks.com/aws/en/compute/standard-limitations)).
- Apache Spark can run the same mode locally: `spark.api.mode=connect` switches a classic application to Spark Connect, and setting `spark.remote` to `local[...]` starts a local Spark Connect server ([application development with Spark Connect](https://spark.apache.org/docs/latest/app-dev-spark-connect.html)).

### Session defaults (T4)

- `spark.sql.session.timeZone` default is "(value of local timezone)"; `spark.sql.sources.default` is `parquet` ([Spark configuration](https://spark.apache.org/docs/latest/configuration.html)).
- Databricks SQL `TIMEZONE` system default is UTC ([TIMEZONE](https://docs.databricks.com/aws/en/sql/language-manual/parameters/timezone)). On Databricks, "if `USING` is omitted, the default is `DELTA`" ([CREATE TABLE USING](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-create-table-using)).
- Runtime 18 moved the default JDK from 17 to 21 and notes that `Double.toString()` and `Float.toString()` output can differ in edge cases and that updated locale data can affect date, time and number formatting ([Runtime 18 LTS notes](https://docs.databricks.com/aws/en/release-notes/runtime/18)). Serverless environments stay on JDK 17 ([environment versions](https://docs.databricks.com/aws/en/release-notes/serverless/environment-version/)).

### Photon and Databricks' Spark patches (T5, T6)

- Photon "replaces the JVM-based Spark SQL execution engine with a native C++ runtime" for supported operations and falls back to Spark otherwise. It is enabled on serverless compute and SQL warehouses and is on by default for classic compute created in the UI; through the Clusters or Jobs API it must be requested with `runtime_engine: PHOTON`. It does not support UDFs, RDD APIs or Dataset APIs. The page states that with fallback "your query still produces correct results" and lists no result differences ([Photon](https://docs.databricks.com/aws/en/compute/photon)).
- Runtime 19 "includes Apache Spark 4.2.0 ... as well as the following additional bug fixes and improvements made to Spark", and its notes list behavioural changes dated after the open-source release ([Runtime 19 notes](https://docs.databricks.com/aws/en/release-notes/runtime/19)). Runtime 18 LTS notes include result-changing fixes such as case-insensitive `NATURAL JOIN` column matching, a `LEFT OUTER JOIN LATERAL` fix behind a `spark.databricks.*` flag, and a corrected `regr_r2` ([Runtime 18 LTS notes](https://docs.databricks.com/aws/en/release-notes/runtime/18)).

### Delta Lake features (T7)

- `MERGE`: open-source Delta documents SQL, Python and Scala merge including `WHEN NOT MATCHED BY SOURCE`, and that a merge can fail when several source rows match one target row ([Delta updates](https://docs.delta.io/latest/delta-update.html)). Databricks: from Runtime 16.0, `MERGE` evaluates `WHEN MATCHED` conditions as well as `ON` to decide duplicate matches; 15.4 LTS and below look at `ON` only ([Databricks MERGE](https://docs.databricks.com/aws/en/delta/merge)). Which rule open-source Delta 4.x applies was not established.
- Identity columns: open-source Delta supports them from 3.3 through the `DeltaTable` builder ([Delta batch](https://docs.delta.io/latest/delta-batch.html)); `GENERATED ALWAYS AS IDENTITY` and `GENERATED BY DEFAULT AS IDENTITY` in `CREATE TABLE` arrived in Delta 4.4.0 ([GitHub releases](https://github.com/delta-io/delta/releases)). The Delta batch page still says SQL is "not supported yet", which the 4.4.0 release notes contradict. On both platforms values are unique and monotonic in step but "not guaranteed to be contiguous", only `BIGINT` is supported, and declaring one disables concurrent transactions ([Databricks identity columns](https://docs.databricks.com/aws/en/delta/generated-columns), [Delta batch](https://docs.delta.io/latest/delta-batch.html)).
- Constraints: Databricks enforces `NOT NULL` and `CHECK`; primary key, foreign key and unique constraints are informational and "aren't enforced" ([constraints on Databricks](https://docs.databricks.com/aws/en/tables/constraints)). Open-source Delta documents "two types of constraints": `NOT NULL` and `CHECK` ([Delta constraints](https://docs.delta.io/latest/delta-constraints.html)).
- Table-feature protocol: Databricks warns that operations available in a runtime "might not be available in the corresponding OSS Delta Lake version" ([feature compatibility](https://docs.databricks.com/aws/en/delta/feature-compatibility)).

### Transactions, procedures, Unity Catalog names (T8, T9, T10)

- Transactions require that all written tables are Unity Catalog managed tables with catalog commits enabled. Non-interactive (`BEGIN ATOMIC`) runs on any SQL warehouse, serverless compute, or a cluster on Runtime 18.0+; interactive (`BEGIN TRANSACTION`) runs on SQL warehouses only ([transactions](https://docs.databricks.com/aws/en/transactions/)). Apache Spark 4.2's SQL syntax reference and scripting page contain no transaction statements ([Spark SQL syntax](https://spark.apache.org/docs/latest/sql-ref-syntax.html), [Spark SQL scripting](https://spark.apache.org/docs/latest/sql-ref-scripting.html)). Delta's release notes describe catalog-managed tables as "unlocking capabilities like multi-table transactions" but document no user-facing transaction statement ([GitHub releases](https://github.com/delta-io/delta/releases)).
- `CREATE PROCEDURE` "applies to Databricks SQL, Databricks Runtime 17.0 and above, Unity Catalog only" ([CREATE PROCEDURE](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-create-procedure)). SQL scripting applies from Runtime 16.3, with cursors and condition handlers from 18.1 ([Databricks SQL scripting](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-scripting)); Apache Spark 4.2 documents the same scripting constructs ([Spark SQL scripting](https://spark.apache.org/docs/latest/sql-ref-scripting.html)).
- "Unity Catalog stores all object names as lowercase"; column name case is preserved but queries are case-insensitive ([names](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-names)).
- The open-source Unity Catalog project documents running Spark and Delta locally against a local Unity Catalog server with three-part names, needing at least Spark 3.5.3 and Delta 3.2.1 ([Unity Catalog Spark integration](https://docs.unitycatalog.io/integrations/unity-catalog-spark/)). Delta's table pairs Unity Catalog 0.5.x with Delta 4.3.x ([releases](https://docs.delta.io/latest/releases.html)). This reproduces naming, not Databricks governance or transactions.

### Databricks-only functions (T11)

- Method: the names in Databricks' [alphabetical list of built-in functions](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-functions-builtin-alpha) (724 parsed) were compared with the function headings in the Apache Spark 4.2.0 [built-in function reference](https://spark.apache.org/docs/latest/api/sql/index.html) (562 parsed). 218 names appear on Databricks only. The comparison is by page scraping and is approximate: operators and syntax-level constructs such as `try_cast` appear in one list and not the other.
- A sample was checked against Spark's own registry at tag `v4.2.0` ([FunctionRegistry.scala](https://github.com/apache/spark/blob/v4.2.0/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/analysis/FunctionRegistry.scala)). Not registered: `getdate`, `charindex`, `iff`, `read_files`, `ai_query`, `hmac`, `secret`, `is_member`, `current_metastore`, `table_changes`, `st_point`, `h3_longlatash3`. Registered: `dateadd`, `datediff`, `datepart`, `len`, `left`, `right`, `isnull`, `ifnull`, `nvl`, `string_agg`, `listagg`, `try_divide`, `to_varchar`.

### Alternatives that close the target-side gap

**Databricks Connect** ([overview](https://docs.databricks.com/aws/en/dev-tools/databricks-connect/), [requirements](https://docs.databricks.com/aws/en/dev-tools/databricks-connect/requirements), [install](https://docs.databricks.com/aws/en/dev-tools/databricks-connect/python/install), [limitations](https://docs.databricks.com/aws/en/dev-tools/databricks-connect/python/limitations))

- What it is: a client library built on Spark Connect. Python runs locally; DataFrame operations and UDFs execute on Databricks compute. It therefore exercises the real runtime, Photon and Unity Catalog, which closes T5, T6, T8, T9, T10 and T11.
- Setup cost: a workspace with Unity Catalog enabled; compute whose runtime version is at least the client's version, either serverless or a cluster whose access mode is "Assigned or Shared" (the requirements page's names); authentication, normally OAuth through the Databricks CLI; local Python 3.12 for clients 16.4 and above (`databricks-connect` on PyPI requires `==3.12.*`; current is 19.2.0).
- It conflicts with `pyspark`: the documented install step is to uninstall PySpark first. The local-PySpark sandbox and a Databricks Connect environment therefore need separate virtual environments.
- It "does not support connecting to open source Apache Spark servers".
- Not available: `SparkContext`, RDDs, libraries that reach the JVM, and `CREATE TABLE ... AS SELECT` (use `spark.sql("SELECT ...").write.saveAsTable(...)`).
- Running cost is the Databricks compute consumed. No price was researched.

**Databricks Free Edition** ([sign-up](https://docs.databricks.com/aws/en/getting-started/free-edition), [limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations))

- No cost, serverless only, quota limited: one 2X-Small SQL warehouse, at most five concurrent job tasks, one workspace and one metastore; compute shuts down for the rest of the day (or month) when quota is exceeded.
- It replaced Community Edition, which was retired in 2025.
- "Free Edition accounts may not be used for commercial purposes", carry no SLA or support, and may be deleted when inactive. Outbound internet access is restricted to trusted domains, and there is no access to account-level APIs.
- Setup cost is an email sign-up. The non-commercial restriction rules it out as the reconciliation environment for a tool used on customer engagements; it is suitable for the project's own exploration.

**Free trial** ([sign-up](https://docs.databricks.com/aws/en/getting-started/free-trial))

- Free usage credits valid for 14 days. Express sign-up needs only an email and gives a serverless workspace with no cloud account; signing up through AWS Marketplace also allows a classic workspace.
- With a payment method on file the account converts to pay-as-you-go when credits run out. Accounts created with personal email addresses may be limited (one SQL warehouse, a 50 DBU per hour cap, limited external network access).
- Setup cost is minutes; it is not a standing environment.

### SQL Server in a container

**Editions and licence terms**

- The image is `mcr.microsoft.com/mssql/server`, "SQL Server running on Linux, based on Ubuntu"; `ACCEPT_EULA` is required and `MSSQL_PID` selects the edition. Requirements: Docker Engine 1.8+, at least 2 GB of RAM and 2 GB of disk ([Docker quickstart](https://learn.microsoft.com/en-us/sql/linux/quickstart-install-connect-docker?view=sql-server-ver17)).
- `MSSQL_PID` values for 2017 to 2022 images: `Evaluation`, `Developer`, `Express`, `Web`, `Standard`, `Enterprise`, `EnterpriseCore`. For 2025: `Evaluation`, `Express`, `StandardDeveloper`, `Standard`, `EnterpriseDeveloper`, `Enterprise`, `EnterpriseCore` ([environment variables](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-configure-environment-variables?view=sql-server-ver17)). The quickstart says a container without `MSSQL_PID` runs "the Developer edition"; it does not say which of the two 2025 Developer editions.
- SQL Server 2025 Enterprise Developer "includes all the functionality of Enterprise edition, but is licensed for use as a development and test system, not as a production server"; Standard Developer is the same for Standard. Evaluation is Enterprise for 180 days. Express is capped at 10 GB per database, 1,410 MB buffer pool and the lesser of one socket or four cores ([editions on Linux, 2025](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-editions-and-components-2025?view=sql-server-ver17)); it is the one free edition licensed for production ([container deployment](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-docker-container-deployment?view=sql-server-ver17)).
- Licence text for 2025 Developer: "You may install and use any number of copies of the software on any device, including third party shared devices, to design, develop, test and demonstrate your programs. You may not use the software in a production environment." End users "may access the software to perform acceptance tests on your programs." Evaluation "will stop running one hundred eighty (180) days after you install it." Benchmark results may not be disclosed to third parties without Microsoft's written approval ([SQL Server 2025 Developer, Express, Evaluation licence terms](https://www.microsoft.com/content/dam/microsoft/usetm/documents/sql-server/sql-server-2025-developer,-express,-evaluation/retail/SQL_Server_2025_Developer_Express_and_Evaluation_Edition_English.pdf)).
- By passing `ACCEPT_EULA=Y` and an edition in `MSSQL_PID` "you express that you have a valid and existing license for the edition and version of SQL Server that you intend to use" ([container deployment](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-docker-container-deployment?view=sql-server-ver17)).
- Reading for this project: a reconciliation sandbox that runs synthetic data to test conversions is development and test use, which the Developer licence permits at no cost. This is a reading of the terms, not legal advice.

**Versions and tags**

- SQL Server 2025 (17.x) is the current version: released 2025-11-18, mainstream support to 2031-01-06, extended to 2036-01-06 ([lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/sql-server-2025)). The lifecycle pages print end timestamps of 06:59:59 on the following day; the dates given here are the calendar day before that timestamp. Extended support ends 2030-01-08 for 2019 and 2027-10-12 for 2017; it ended 2026-07-14 for 2016, which is now in paid Extended Security Updates ([2019](https://learn.microsoft.com/en-us/lifecycle/products/sql-server-2019), [2017](https://learn.microsoft.com/en-us/lifecycle/products/sql-server-2017), [2016](https://learn.microsoft.com/en-us/lifecycle/products/sql-server-2016)).
- The registry lists tags for 2017, 2019, 2022 and 2025 only. The newest fixed tags on 2026-10-13 are `2025-CU9-ubuntu-24.04`, `2022-CU27-ubuntu-22.04`, `2019-CU32-GDR11-ubuntu-20.04` and `2017-CU31-GDR18-ubuntu-18.04`, alongside floating `2025-latest`, `2022-latest`, `2019-latest`, `2017-latest` and `latest` ([registry tag list](https://mcr.microsoft.com/v2/mssql/server/tags/list)).
- Compatibility levels: SQL Server 2025 supports 170 down to 100; 2022 supports 160 down to 100. A database restored from an earlier version "keeps its existing compatibility level". Compatibility level protects against some breaking changes but "discontinued functionality ... is not protected by compatibility level" ([compatibility level](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-database-transact-sql-compatibility-level?view=sql-server-ver17)).

**What the Linux container lacks compared with Windows**

- Baseline: SQL Server on Linux "uses the same SQL Server Database Engine as SQL Server on Windows ... including bare metal, virtual machines, and containers", so "most features behave identically across platforms" ([overview](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-overview?view=sql-server-ver17)).
- Unsupported on Linux for SQL Server 2025, from the [editions on Linux page](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-editions-and-components-2025?view=sql-server-ver17):
  - Database engine: merge replication; distributed query with third-party connections; linked servers to data sources other than SQL Server; system extended stored procedures (`xp_cmdshell`, etc.); FileTable and FILESTREAM; CLR assemblies with the `EXTERNAL_ACCESS` or `UNSAFE` permission set; buffer pool extension.
  - SQL Server Agent: the CmdExec, PowerShell, Queue Reader, SSIS, SSAS and SSRS subsystems; alerts; managed backup.
  - Security: Windows integrated authentication for linked servers; Always Encrypted with secure enclaves.
  - Services: SQL Server Browser, Analysis Services, Reporting Services, R services as a separate package.
  - Features that depend on the Azure Arc agent are not supported in containers.
- SQL Server Agent ships in the engine package, is disabled by default, and is enabled in a container with `MSSQL_AGENT_ENABLED=true` ([Agent on Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-setup-sql-agent?view=sql-server-ver17), [environment variables](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-configure-environment-variables?view=sql-server-ver17)). Microsoft's tutorial creates and schedules a T-SQL job on Linux ([Agent jobs on Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-run-sql-server-agent-job?view=sql-server-ver17)).
- SSIS: "Installing SSIS on containers is also not supported" ([install SSIS on Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-setup-ssis?view=sql-server-ver17)); "SSIS isn't available for SQL Server 2025 (17.x) on Linux"; where it is available (2017 to 2022 on Ubuntu or RHEL) it has no SSIS Catalog database and no scheduled execution by Agent ([SSIS on Linux limitations](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-ssis-known-issues?view=sql-server-ver17)).
- Full-Text Search is a separate package, `mssql-server-fts` ([install Full-Text Search on Linux](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-setup-full-text-search?view=sql-server-ver17)), and "not all filters are available on Linux, including filters for Microsoft Office documents" ([known issues](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-known-issues?view=sql-server-ver17)). Microsoft's sample repository shows a custom image that installs it ([example Dockerfile](https://github.com/microsoft/mssql-docker/blob/master/linux/preview/examples/mssql-agent-fts-ha-tools/Dockerfile)); that example targets SQL Server 2017 on Ubuntu 16.04 and is out of date.
- Other Linux limits: one instance per host (use one container per instance); a database backed up on Windows must be restored `WITH MOVE`; SQL Server 2014 databases that use In-Memory OLTP cannot be restored to Linux ([known issues](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-known-issues?view=sql-server-ver17)).
- Host support: "SQL Server container images are supported only on Linux hosts running on Intel and AMD x86-64 CPUs. Emulation or translation environments (for example, Rosetta 2, Prism, or QEMU) aren't tested or supported" ([Docker quickstart](https://learn.microsoft.com/en-us/sql/linux/quickstart-install-connect-docker?view=sql-server-ver17)). "SQL Server deployments in Windows containers aren't covered by support" ([container deployment](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-docker-container-deployment?view=sql-server-ver17)).

**Collations**

- `MSSQL_COLLATION` "sets the default collation for SQL Server" and overrides the language-ID mapping ([environment variables](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-configure-environment-variables?view=sql-server-ver17)); after setup, `mssql-conf set-collation` "changes the collation value to any of the supported collations" ([mssql-conf](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-configure-mssql-conf?view=sql-server-ver17)).
- The server collation is the default for system databases and newly created user databases, and applies to string columns of "the objects in tempdb (for example, temporary tables)"; the US English default is `SQL_Latin1_General_CP1_CI_AS` ([set or change the server collation](https://learn.microsoft.com/en-us/sql/relational-databases/collations/set-or-change-the-server-collation?view=sql-server-ver17)).
- None of the Linux pages read (editions, known issues, mssql-conf, environment variables) lists a collation that is unavailable on Linux. That is absence of a documented restriction, not a documented guarantee of parity.

**Sample databases**

- WideWorldImporters: Microsoft publishes a tutorial that restores `WideWorldImporters-Full.bak` into a `2022-latest` or `2025-latest` container: copy the file in with `docker cp`, read logical names with `RESTORE FILELISTONLY`, then `RESTORE DATABASE ... WITH MOVE` for the four files, one of which is the In-Memory OLTP filegroup ([restore tutorial](https://learn.microsoft.com/en-us/sql/linux/tutorial-restore-backup-in-sql-server-container?view=sql-server-ver17)). The Full sample needs "SQL Server Evaluation/Developer/Enterprise Edition" and uses temporal tables, In-Memory OLTP with a natively compiled procedure, columnstore indexes, row-level security, dynamic data masking and JSON; its full-text indexes are created by a post-install procedure and need Full-Text Search installed ([install](https://learn.microsoft.com/en-us/sql/samples/wide-world-importers-oltp-install-configure?view=sql-server-ver17), [features used](https://learn.microsoft.com/en-us/sql/samples/wide-world-importers-oltp-use-of-sql-server-features?view=sql-server-ver17)). The backup is from the [v1.0 release](https://github.com/Microsoft/sql-server-samples/releases/tag/wide-world-importers-v1.0), whose notes say "for SQL Server 2016 SP1 (or higher), any edition"; the two pages disagree on edition, and a Developer edition satisfies both.
- AdventureWorks: backups are published per version, including `AdventureWorks2025.bak`, `AdventureWorksDW2025.bak` and `AdventureWorksLT2025.bak`, and the guidance is to use the one matching the server version. Microsoft documents the Linux restore with `MOVE` clauses to `/var/opt/mssql/data/` ([install and configure](https://learn.microsoft.com/en-us/sql/samples/adventureworks-install-configure?view=sql-server-ver17), [release](https://github.com/Microsoft/sql-server-samples/releases/tag/adventureworks)). The install script for the OLTP database creates a full-text catalog and three full-text indexes and tells the user to enable full-text search first ([instawdb.sql](https://github.com/microsoft/sql-server-samples/blob/master/samples/databases/adventure-works/oltp-install-script/instawdb.sql)).
- So both restores are documented by Microsoft for Linux, and WideWorldImporters specifically for the container. Neither was run here.

### Connecting the two halves

- Spark's JDBC source needs "the JDBC driver for your particular database on the spark classpath" ([JDBC data source](https://spark.apache.org/docs/latest/sql-data-sources-jdbc.html)). If local Spark reads from the container, the sandbox must supply Microsoft's JDBC driver; current driver jars are published for JRE 8 and JRE 11 baselines ([support matrix](https://learn.microsoft.com/en-us/sql/connect/jdbc/microsoft-jdbc-driver-for-sql-server-support-matrix?view=sql-server-ver17)). Whether those jars are supported on the JDK 17 or 21 that Spark 4 requires was not checked.

## Implications for other tickets

For the task that builds the SQL Server container:

- Pin a fixed image tag (for example `2025-CU9-ubuntu-24.04`), not `latest` or `2025-latest`, so reconciliation results are reproducible.
- Set `MSSQL_PID` explicitly. On 2025 images the values are `EnterpriseDeveloper` or `StandardDeveloper`; `Developer` is listed only for 2022 and earlier. The Full WideWorldImporters sample needs Enterprise-level features.
- Set `MSSQL_COLLATION` at first start and make it configurable, since it governs `tempdb`.
- Restore with `WITH MOVE` to `/var/opt/mssql/data/`, and use the AdventureWorks backup that matches the image version.
- Decide whether Full-Text Search is in scope. If it is, plan for a custom image that installs `mssql-server-fts`, and verify the stock image first.
- Give the container at least 2 GB of RAM, and expect an x86-64 Linux host or VM. Apple-silicon machines are outside Microsoft's supported configuration.
- Consider parameterising the image version (2019, 2022, 2025) so the sandbox can match a customer's production version, with compatibility level as the fallback for older sources.

For the decision "How does reconciliation generate data and compare results?":

- Pin `pyspark`, `delta-spark`, Python and JDK to a named target runtime and record that runtime in the conversion report.
- Set ANSI mode, session time zone and table format explicitly rather than inheriting local defaults, and run the local session in Spark Connect mode if serverless or standard-access compute is the target.
- Never compare identity-column values across platforms.
- Treat "cannot run in the sandbox" (S3, S5, S6, T8, T9, T11) as its own outcome, distinct from "did not reconcile".
- If reconciliation against real Databricks is wanted, Databricks Connect needs its own virtual environment because it cannot coexist with `pyspark`, and Free Edition cannot be used for commercial work.
