# How existing migration tools divide work between rules and LLMs

Research for [issue #3](https://github.com/Bach-To-The-Future/data-migration/issues/3). Sources were read on 2026-10-13. Every claim cites the source that owns it. Where a claim rests on marketing rather than documentation or code, it says so. Where something could not be established, it is listed in [Not established](#not-established) and not guessed.

Terms follow `CONTEXT.md`: source, target, artefact, core, conversion report, flagged fragment, escape hatch, reconciliation. "LLM step" means one model call with a fixed prompt at a fixed point in a pipeline. "Agent" means a model in a loop choosing its own next step and tools.

## Answer

Eight patterns repeat across the tools surveyed.

1. **Deterministic conversion runs first and the LLM gets only what is left over.** Snowflake, AWS and Microsoft all convert with a rule-based engine and offer the model only the objects or statements that engine could not finish. Snowflake states it outright: "Source SQL is translated deterministically by SnowConvert before AI touches it" ([Snowflake AIM overview](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/overview)). AWS limits generative AI to a published list of action-item codes and converts "all other SQL elements" with rules ([AWS DMS gen AI](https://docs.aws.amazon.com/dms/latest/userguide/schema-conversion-convert.databaseobjects.html)). The two exceptions are both from Databricks: Switch and the agentic code converter are LLM-first. Switch is offered as an alternative to the deterministic transpilers, not as a stage after them, and the agentic converter's documentation does not mention them.

2. **Inside a vendor pipeline the model is an LLM step or a bounded fix loop, not a free agent.** Switch is a fixed seven-step pipeline with one conversion call per file and a `for` loop of at most `max_fix_attempts` repairs (default 1). AWS, Google and Microsoft each call the model at a fixed point, once per statement, file or object. Agents appear in two places only: as a per-artefact worker that converts, validates and retries (Databricks agentic converter, Snowflake's test-driven fix loop), and as an outer driver that operates the deterministic tool through an API (AWS and Google expose their services to coding agents over MCP; Snowflake ships a skill tree for its coding agent). No surveyed tool documents an orchestrator agent that decides how conversion itself is carried out.

3. **Every fix loop is driven by a deterministic oracle.** The model is never asked whether its own output is right. Switch feeds back `ast.parse` and `EXPLAIN` errors. Snowflake feeds back a mismatch between source output and Snowflake output. The published research systems do the same with compilers and test runs.

4. **Deterministic engines report what they could not convert with a code, a location and a severity. LLM converters report far less.** Snowflake has four coded categories, four severity levels for the main one, and an inline marker that breaks compilation. AWS has numbered action items with effort estimates. Morpheus gives `[line:column]` errors and separates errors from warnings. Google gives severity, category, line and column. By contrast Switch asks the model to leave unconvertible parts as Python comments, and the Databricks agentic converter shows a colour per file.

5. **LLM output is labelled and never trusted on its face.** AWS replaces the original action items with a single code (7744 for SQL Server) wherever the model wrote the statement. Google keeps the model's result as a separate "Gemini suggestion" beside the rule-based translation. Microsoft and AWS both tell the user in the documentation to verify it. Snowflake marks an object complete only when its test passes or the user skips it.

6. **Validation comes in three tiers and most tools stop at the first.** Tier one is "does the target accept it": `EXPLAIN`, `ast.parse`, or running the `CREATE`. Almost every tool does this. Tier two is running source and conversion on the same inputs and comparing results, which is what `CONTEXT.md` calls reconciliation. Only Snowflake documents how it does this. Tier three is comparing migrated tables, which several vendors ship as a separate tool (Lakebridge Reconcile, Google's Data Validation Tool, Snowflake's L1 to L3 checks) and which says nothing about whether the code was converted correctly.

7. **The target is SQL almost everywhere.** Given T-SQL, six of the eight tools emit only the target's SQL dialect and its procedural language. Where Python is produced from T-SQL, it is Python that wraps SQL strings in `spark.sql()`: Switch's prompt instructs the model to do exactly that, and BladeBridge's stored-procedure rule file does it with templates. The single exception is the Databricks agentic code converter, whose documentation (dated 2026-09-11) lists a "Notebooks" target described as "Databricks notebooks that use the DataFrame API, with `spark.sql` for logic that is clearer in SQL". It is in Beta, it is LLM-produced, and its documentation does not mention stored procedures. **No deterministic tool was found that emits DataFrame API code from T-SQL stored procedures.**

8. **No surveyed tool documents one intermediate representation shared across several sources and several targets.** The tree-based engines (Morpheus, SnowConvert) parse to a tree, transform it and print it, but each serves exactly one target. BladeBridge ships one rule file per source and target pair with inheritance between files. Switch ships one prompt file per source. Google names its translation tasks per pair (`SQLServer2BigQuery_Translation`). Tools extend to new sources by adding a front end or a rule file. None shows how a second target is added without a second engine.

Two smaller patterns are worth carrying forward. First, every tool gives the user a way to turn a recurring manual fix into a reusable rule (BladeBridge JSON overrides, Switch prompt files, Databricks skills, Snowflake's rule engine, Google's configuration YAML), which moves work from the model back to rules over time. Second, units handed to a model are kept small: one statement at AWS, one file under 20,000 tokens for Switch, one script under 1,000 lines for the Databricks agentic converter.

## Detail by tool

### Databricks Lakebridge

Lakebridge "comes with three transpilation plugins", grouped in its guide as "Deterministic Conversion (BladeBridge & Morpheus)" and "LLM-Powered Conversion (Switch)" ([transpile guide](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/index.mdx)). Databricks describes them as "_Morpheus_, its AST-based transpiler, _BladeBridge_, a pattern-based transpiler, and _Switch_, an LLM-powered transpiler" ([pluggable transpilers](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/pluggable_transpilers/index.mdx)).

The three are alternatives chosen per run, not stages of one pipeline. Lakebridge "can only use 1 at a given point in time" and talks to each over the Language Server Protocol (same pluggable transpilers page). The plugin boundary is therefore the only thing the three share. There is no common representation between them.

The supported-dialects table in the transpile guide gives the target for each: for `mssql`, BladeBridge and Morpheus produce "DBSQL" and Switch produces "SparkSql". "PySpark" appears in that table only for DataStage through BladeBridge.

Only the Lakebridge host is open source. `databrickslabs/switch`, `databrickslabs/bladerunner` and `databrickslabs/morpheus` do not resolve as public repositories (checked with `gh repo view` on 2026-10-13). Switch and BladeBridge are published as wheels on PyPI, which were downloaded and read. Morpheus is distributed as a jar on Maven Central and was not decompiled.

#### Morpheus

- Pipeline in three stages. Parse: "The input SQL is parsed into an intermediate representation (IR) tree." Transform: "The IR tree undergoes a series of transformations that convert source-dialect constructs into their Databricks SQL equivalents." Code gen: "The transformed tree is fed to a code generator that produces and formats the final Databricks SQL text." The parser is "generated from a carefully crafted ANTLR grammar" ([Morpheus](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/pluggable_transpilers/morpheus/index.mdx)).
- Scope: `mssql`, `snowflake`, `synapse`. "Morpheus targets **Databricks SQL** only." Extensibility is given as "Not extensible (fixed grammar)" ([choosing tools](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/choosing_tools.mdx)).
- Reporting: it "accumulates every error and warning encountered during the transform and code-gen phases but continues processing the file". Output starts with a header comment, for example `[3:5] Function GIBBERISH cannot be translated to Databricks SQL`. A parse error stops the tree being built, and the original text is returned with error annotations (Morpheus page).
- Guarantee model: no errors and no warnings means "output is equivalent to input on the source platform". A warning means Morpheus "could not confirm equivalence". An error means it "knows equivalent results cannot be guaranteed". Stated caveats are statistical functions and row order without `ORDER BY`. It "does not perform semantic validation (e.g., type-checking) on the input SQL" (Morpheus page).
- No LLM is mentioned anywhere on the Morpheus page.

The useful idea here is the three-way outcome. A construct is converted with a guarantee, converted with a caveat, or reported as not convertible. That is the same split `CONTEXT.md` gives the conversion report.

#### BladeBridge

- The docs call it "a code conversion engine" that "runs based on a configuration file" ([BladeBridge](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/pluggable_transpilers/bladebridge/index.mdx)). It "relies heavily on rules defined inside configuration files", which are "a set of layered json files and code templates" ([BladeBridge configuration](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/pluggable_transpilers/bladebridge/bladebridge_configuration.mdx)).
- Rule types are `line_subst`, `block_subst` and `function_subst`, "executed in the order given", where "longer and more specific patterns should typically preceed shorter and more generic patterns" (same configuration page). These are regular-expression rewrites. For example the shipped SQL Server rules contain `{"from" : "\bEXEC\b", "to" : "CALL"}` and `{"from" : "\bGO\b", "to" : ""}` (file `Converter/Configs/MSSQL/mssql2databricks_sql.json` in the [databricks-bb-plugin 0.3.0 wheel](https://pypi.org/project/databricks-bb-plugin/0.3.0/)).
- The wheel contains a closed platform binary (`Converter/bin/{Linux,MacOS,Windows}/dbxconv`), the JSON rule files, and Perl hook files such as `MSSQL/mssql_hooks.pl` (wheel file listing, same PyPI page). The Python in the wheel is a thin wrapper that writes the source to a temp directory and runs the binary (`databricks/labs/bladebridge/transpiler.py`).
- Rule files are pairwise. `Converter/Configs/tech_mapper_main.json` maps each source and target type to one file, for example `"MSSQL": {"source-type": "SQL", "targets": {"SQL": "base_sqlserver2databricks_sql.json"}}`. Files inherit from each other with `inherit_from`; the SQL Server file inherits `base_tsql2databricks_sql.json`, which is how Synapse and SQL Server share T-SQL rules.
- For SQL sources the docs say "SQL dialects always output Databricks SQL", and for procedures "source stored procedures are translated to Databricks SQL scripting equivalents" (configuration page and BladeBridge page).
- The wheel also ships `Converter/Configs/MSSQL/mssql_procs2databricks_sql_python.json`, with `"target_file_extension" : "py"`. It splits a procedure into fragments by regex and wraps each in a template such as `"default_sql_wrapping": "%DF% = spark.sql(f\"\"\"\n%SQL%\n\"\"\")"`, turns parameters into `dbutils.widgets`, and turns `EXISTS (...)` into `spark.sql("""...""").count() > 0`. The file contains no DataFrame method calls. It is not referenced by `tech_mapper_main.json`, so the `mssql` dialect in Lakebridge does not reach it.
- Reporting at the wrapper level is one diagnostic for the whole file, code `PARSING-FAILURE` when the binary exits non-zero and `CONVERSION-FAILURE` when no output is found (`transpiler.py`).
- The wheel ships `PlatformGaps/platform_source_gaps.json`, a table of regex patterns with `supported`, `desc`, `complexity` and `conversion_strategy` fields, for example `SELECT TOP` for MSSQL with strategy "USE LIMIT". How the binary uses it was not established.

#### Switch

All of the following is from the [databricks-switch-plugin 0.2.0 wheel](https://pypi.org/project/databricks-switch-plugin/0.2.0/) and the [Switch architecture page](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/transpile/pluggable_transpilers/switch/architecture.mdx).

- It is a fixed pipeline run as a Databricks Job. `00_main` "validates parameters and routes to the appropriate orchestrator based on `target_type`". The notebook orchestrator calls, in order, `analyze_input_files`, `convert_with_llm`, a validator, `fix_syntax_with_llm`, `split_code_into_cells`, `export_to_notebook`, and optionally `convert_notebook_to_sql`. The "orchestrator" is ordinary Python that calls `dbutils.notebook.run` for each step (`notebooks/orchestrators/orchestrate_to_notebook.py`). No model chooses the next step.
- The conversion call sends a system message, few-shot examples and the file. The only loop inside it continues a response that was cut off: when `finish_reason` is `"length"` it appends the partial answer and asks the model to "continue exactly from this point" (`notebooks/pyscripts/helpers/batch_inference_helper.py`).
- The repair loop is `for attempt in range(max_fix_attempts)`: validate, count files with errors, stop if none, otherwise call `fix_syntax_with_llm` (`orchestrate_to_notebook.py`). The default is 1 and 0 disables it (architecture page).
- Validation: "Checks Python syntax using `ast.parse()` and validates SQL statements within `spark.sql()` calls using Spark's `EXPLAIN` command." (architecture page). The fix prompt begins "Fix the following errors in the Python code running in a Databricks notebook. The code contains Spark SQL queries, and most errors are Spark SQL-related." (`notebooks/processors/fix_syntax_with_llm.py`).
- There is one prompt file per source under `resources/builtin_prompts/sql_to_databricks_python_notebook/`: `mssql.yml`, `mysql.yml`, `netezza.yml`, `oracle.yml`, `postgresql.yml`, `redshift.yml`, `snowflake.yml`, `teradata.yml`. Each embeds a shared block from `common/sql_to_databricks_notebook_common_python.yml`. The shared block is the nearest thing to a core, and the per-source files hold function mappings, type mappings and worked examples.
- The shared prompt fixes the output shape: "Use `spark.sql()` to execute SQL statements. Write SQL statements directly within `spark.sql()`." It also says "DO NOT omit any part of the conversion. Instead, include any non-convertible parts as Python comments in the output code". For T-SQL it adds: "For T-SQL statements with no direct equivalent (e.g., `CREATE NONCLUSTERED INDEX`, `EXEC <Procedure>`, etc.), exclude or comment them out."
- The prompt does tell the model to "Replace cursor/row-by-row logic with Spark DataFrame operations", to simulate transactions with `try-except-finally` and `RESTORE TABLE TIMESTAMP AS OF`, and to replace temp tables with Delta tables dropped at the end. These are instructions to a model, not checked rules.
- Input size is capped. `analyze_input_files` counts tokens and "Files exceeding `token_count_threshold` are excluded from conversion." (architecture page). The orchestrator lists them under the heading "Files exceeding threshold: Need manual review."
- Results live in a Delta table whose columns include `is_conversion_target`, `result_content`, `result_error`, `result_python_parse_error`, token counts and timings (`notebooks/processors/analyze_input_files.py`). The table is how the pipeline carries state between steps and how a run can be resumed from an `existing_result_table`.
- Databricks labels Switch "Experimental" and says "generated notebooks may require manual adjustments" ([choosing tools](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/choosing_tools.mdx)).

#### Lakebridge validation and Reconcile

- Transpile-time validation runs `EXPLAIN` on each output query through a SQL backend. Syntax errors and unresolved routines fail. `TABLE_OR_VIEW_NOT_FOUND` is downgraded to a warning ([`helpers/validation.py`](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/src/databricks/labs/lakebridge/helpers/validation.py)).
- Lakebridge Reconcile "validates data fidelity after migration by comparing your source system against the Databricks target" at schema, row-hash and column level ([reconcile guide](https://github.com/databrickslabs/lakebridge/blob/b9cfdf3a466091f00fa14adcaacd0ad7afd9b0b8/docs/lakebridge/docs/reconcile/index.mdx)). It compares tables. It does not run a source artefact and its conversion on the same input.

### Databricks agentic code converter

This is a separate, newer product from the Lakebridge transpilers. Sources are the [Databricks documentation page](https://docs.databricks.com/aws/en/migration/agentic-code-converter) (last updated 2026-09-11) and the [launch blog](https://databricks.com/blog/convert-proprietary-code-open-ansi-sql-agentic-code-converter-now-beta) (2026-07-30).

- Status: "This feature is in Beta." (documentation).
- Mechanism: "When you run a conversion, Genie Code invokes the migration skill and deploys subagents that convert files concurrently." "Each subagent analyzes the source dialect, generates the equivalent code for the project's target framework", "validates the result, and retries sections that fail" (documentation). The blog adds "Each subagent iteratively fixes errors, validating both syntax and semantic intent".
- Targets: "Notebooks: Databricks notebooks that use the DataFrame API, with `spark.sql` for logic that is clearer in SQL", or SQL for "ANSI-compliant Databricks SQL queries" (documentation). The blog describes only the SQL target.
- Sources: T-SQL, Snowflake, Redshift, Oracle, BigQuery, Teradata (documentation).
- Limits: "A batch can contain a maximum of 300 files." "A script can contain a maximum of 1,000 lines." (documentation).
- Reporting: files are marked green, yellow, red or grey (documentation). The blog describes a to-do list for flagged files and a proof of concept where 6 of 8 files converted and two stored-procedure files needed manual review.
- Customisation: "Custom skills let you encode business rules that Genie Code applies automatically during every conversion", written as a `SKILL.md` file (documentation).
- Validation: the documentation says the converter "validates that the converted output is syntactically valid and semantically equivalent to the source" but its own testing advice is for the user to run the output and "confirm that the output is semantically correct, not only syntactically valid".
- The documentation links the Lakebridge Analyzer as an optional input for complexity and lineage. It does not mention Morpheus, BladeBridge or Switch.

The architectural claims above come from product documentation, which is short. The blog is a launch post and its framing ("the next generation of data warehouse migration tooling") is marketing. Neither gives a retry bound, a validation method, or an accuracy figure.

### Snowflake SnowConvert AI and the AIM Agent for Data Warehouses

Snowflake's migration documentation is now organised under "Snowflake AIM Agent for Data Warehouses", with SnowConvert AI as its deterministic engine. The older "AI verification" page redirects into this set.

- Engine design, from a Snowflake engineering blog: "SnowConvert is a type of tool known in computer science as a transpiler, or a source-to-source compiler." "Internally, SnowConvert processes the code in two stages: the frontend transpiler and the backend transpiler." The frontend "has three components: a scanner, a parser and a semantic analyzer", producing an intermediate representation "typically represented using an Abstract Syntax Tree (AST)". A transformer rewrites the tree and a pretty printer emits code ([Snowflake engineering blog, 2024-11-14](https://www.snowflake.com/en/engineering-blog/accelerate-code-conversion-data-warehouse-migration/)). An earlier post adds that it "parses your code into an Abstract Syntax Tree (AST) and creates an in-memory Symbol Table" ([Snowflake engineering blog, 2024-09-07](https://www.snowflake.com/en/engineering-blog/accelerate-code-conversion-for-migrations-to-snowflake-with-snowconvert-now-available-for-free-table-conversion-assessments/)).
- Two layers: "SnowConvert applies repeatable, grammar-based translation to your source SQL." "The same input always produces the same output, giving you a high-fidelity baseline instead of a best-effort rewrite." Then "AI explains the issue in context, proposes a fix, and applies it interactively against the same converted code" ([code conversion](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/code-conversion/intro)).
- One source skips the deterministic layer. SAS uses "an AI-based approach rather than the deterministic layer" (same page). Snowflake chose LLM-only where it had no parser.
- Agent structure: the agent "is organized as a skill tree" where the "root skill detects your project state and delegates to the right sub-skill". Sub-skills include connection, register-code-units, convert, assessment, migrate-objects, baseline-capture and rule-engine. It "guides you through six stages": Connect, Init, Register, Convert, Assess, Migrate ([overview](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/overview)).
- Rules have two modes. Regex rules are applied mechanically. For AI-guided rules, "The rule provides context and strategy; the AI interprets and applies it." (overview).
- Reporting: "When a code segment cannot be completely converted, an Error, Warning, and Issue (EWI) message is generated." Codes look like `SSC-EWI-TS0003` for SQL Server. EWIs are "categorized into four severity levels based on the average effort required to fix the code". Each is preceded in the output by a `!!!RESOLVE EWI!!!` marker that "causes compilation to fail". Functional Difference Messages and Performance Review messages are added as comments to code that compiles. Out Of Scope units are excluded from the conversion rate ([issues and troubleshooting](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/code-conversion/issues-and-troubleshooting/README)).
- Testing: "Testing verifies that a converted stored procedure or UDF behaves the same on Snowflake as it did on the source system." The pipeline is Seed, Capture, Validate. "The source database is the reference." "Any mismatch drives an automated fix loop until the two sides agree." ([testing overview](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/testing/overview)).
- Test cases come "from a query-log CSV, from the source database, or synthesized from the source SQL". A Synthetic Testbed Generator supplies "constraint-aware table data and a query log". The conversion runs on "a fresh, isolated clone of the workload database". The comparison covers multiple result sets and output parameters and "compares the table changes, not just a return value" ([procedures and UDFs](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/testing/sprocs-and-udfs)).
- The fix loop classifies a failure before changing code. A dependency failure is reported and skipped. A conversion failure is patched and only the failed cases are rerun. It continues "until they pass or you decide to skip the object" (same page). No iteration cap is documented.
- When there are no query logs, "A swarm of specialized agents generates test cases covering business logic" (overview). This is the only place Snowflake's documentation describes multiple agents, and the task is test generation, not conversion.
- Target: SQL Server procedures have two translation references, "CREATE PROCEDURE (JavaScript)" and "CREATE PROCEDURE (Snowflake Scripting)" ([Transact translation reference](https://docs.snowflake.com/en/migrations/aim-for-datawarehouses/code-conversion/translation-references/transact/README)). Python is not mentioned.

### AWS Schema Conversion Tool and DMS Schema Conversion

DMS Schema Conversion "is a fully managed, web-based feature that builds on the AWS Schema Conversion Tool (AWS SCT) conversion engine" ([DMS Schema Conversion](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_SchemaConversion.html)). SCT remains as a desktop tool.

- Engine: "DMS Schema Conversion converts your schema with a rules-based engine. The rules produce consistent, repeatable results". "When the rules can't fully convert an object, DMS Schema Conversion can use generative AI to convert more of it" (same page).
- Scope of the model: "Generative AI-assisted schema conversion focuses on specific SQL elements with designated action items. All other SQL elements are converted using default rule-based approaches." The page lists the action items per conversion path. For SQL Server to PostgreSQL they include 7628 "PostgreSQL does not support GOTO statements", 7637 "global cursors", 7639 "dynamic cursors" and 7627 "cannot convert this syntax element" ([gen AI conversion](https://docs.aws.amazon.com/dms/latest/userguide/schema-conversion-convert.databaseobjects.html)). The unit is one statement, and the trigger is a named rule failure.
- It is opt-in ("enable the Convert schema with Generative AI option") and available only for Oracle, SQL Server, SAP ASE and Db2 to PostgreSQL targets (same page).
- Labelling: "If the source statement is converted with multiple action items and at least one action item is processed using generative AI, then all Action Items are replaced by one action item 5444 on a target for Oracle and 7744 for Microsoft SQL Server." (same page).
- Stated limits: "As a probabilistic system, generative AI-assisted Schema Conversion may not achieve 100 percent accuracy in all conversions. It can also produce different results for the same SQL statements over a period of time. You must review and validate all conversion outputs." It is not supported for dynamic SQL, triggers, defaults, computed columns and several other elements. A per-account quota of 48 or 80 statements per minute applies (same page).
- Agents: "You can use AI agents to drive DMS Schema Conversion workflows through the AWS API." This means a general coding agent ("Kiro CLI, Claude Code, or Cursor") connected to the AWS MCP server, plus an installable skill holding "API patterns, system schema exclusions, operation sequencing, and service best practices". AWS says the skill exists to "prevent common errors that AI agents make" and "reduce trial-and-error loops" ([AI agents with DMS Schema Conversion](https://docs.aws.amazon.com/dms/latest/userguide/sc-genai-agents.html)). The agent creates projects, runs conversions and exports reports. It does not write the converted code.
- Reporting: the conversion assessment report "identifies which objects DMS Schema Conversion can convert automatically and which objects require manual action", with "estimates showing how much effort is required". The CSV export has one file with "one row per action item occurrence", one "per action item type, with effort values", and one "per object type, with complexity counts" ([assessment reports](https://docs.aws.amazon.com/dms/latest/userguide/assessment-reports.html)). In SCT, selecting an action item highlights the schema item it applies to and shows a recommendation ([SCT action items](https://docs.aws.amazon.com/SchemaConversionTool/latest/userguide/CHAP_AssessmentReport.ActionItems.html)).
- Extension packs: where the target lacks a feature, an extension pack "emulates some of them" (DMS Schema Conversion page). This is AWS's version of the escape hatch, built as a runtime library on the target.
- Targets: SCT lists OLTP and data-warehouse conversions between relational engines, and ETL conversions including "Microsoft SQL Server Integration Services (SSIS) ETL packages" to "AWS Glue or AWS Glue Studio" ([What is AWS SCT](https://docs.aws.amazon.com/SchemaConversionTool/latest/userguide/CHAP_Welcome.html)). No path converts T-SQL stored procedures to Spark code.

### Google BigQuery Migration Service

- Scope: "The translation services automate the conversion of your SQL queries into GoogleSQL, including Gemini-enhanced SQL customization" ([migration intro](https://docs.cloud.google.com/bigquery/docs/migration-intro)). SQL Server T-SQL is listed under dialects "supported in preview", with task type `SQLServer2BigQuery_Translation` ([supported dialects](https://docs.cloud.google.com/bigquery/docs/enable-sql-translations#supported_sql_dialects)).
- The model is configured by rules, not left free. "The Translation service can call Gemini model to generate suggestions to your translated SQL query based on your AI configuration YAML file." A rule has an `instruction` ("In natural language, describe a change to the target SQL"), optional `examples`, and a `rewrite_target` of `SOURCE_SQL` or `TARGET_SQL` ([configuration YAML](https://docs.cloud.google.com/bigquery/docs/config-yaml-translation)).
- Position in the pipeline: with source rules "the translator transforms the original input first and then translates the Gemini-enhanced input". With target rules "the transformation is applied to the translated result as a Gemini-enhanced output", which the user opens with a "Gemini suggestion" button ([batch SQL translator](https://docs.cloud.google.com/bigquery/docs/batch-sql-translator)). The model sits before or after the deterministic translator and never replaces it.
- Other model uses: a `TRANSLATION_EXPLANATION` suggestion type that summarises "differences and inconsistencies between the source SQL query and the translated GoogleSQL query" (configuration YAML page), and inferred source DDL for `RelationNotFound` or `AttributeNotFound` issues, which the user applies and reruns (batch SQL translator page).
- Deterministic configuration is separate and larger: `object_rewriter`, `experimental_statement_rewriter`, `metadata`, `environment`, `optimizer` and others (configuration YAML page).
- Metadata matters: "Translation works best with metadata DDLs. When SQL object definitions can't be found, the translation engine raises `RelationNotFound` or `AttributeNotFound` issues." (batch SQL translator page). The translator resolves names against table shapes, which matches the role `CONTEXT.md` gives table shape.
- Reporting: a translation summary CSV with file, line, column, object name, severity ("either warning or error"), category, source type (SQL or METADATA), message, script context and recommended action (batch SQL translator page).
- Missing functions are covered by helper UDFs: translated queries "initially reference them using the format `bqutil.<dataset>.<function>()`" (same page). This is another target-side emulation library.
- Validation: "Translation is done on a best effort basis. Whenever possible, validate the translated queries." (same page). The Data Validation Tool is a separate open-source tool to "validate that your source and destination tables match" (migration intro).
- Agents: a BigQuery Migration Service MCP server lets external AI applications perform "translating SQL queries into GoogleSQL syntax, generating DDL statements from SQL input queries, and getting explanations of SQL translations" ([MCP server](https://docs.cloud.google.com/bigquery/docs/use-bigquery-migration-mcp)). As at AWS, the agent is a client of the deterministic service.

### Microsoft: SQL Server to Fabric

- The Fabric Migration Assistant "copies metadata and data from the source database, and it automatically converts the source schema to Fabric Data Warehouse. AI-powered assistance provides quick solutions for migration incompatibility or errors." It takes a DACPAC or a direct connection and covers tables, views, functions, stored procedures and security objects ([Migration Assistant](https://learn.microsoft.com/en-us/fabric/data-warehouse/migration-assistant), page updated 2026-09-29).
- Conversion: "the Migration Assistant translates T-SQL metadata to supported T-SQL syntax in Fabric Data Warehouse" ([migrate by uploading a file](https://learn.microsoft.com/en-us/fabric/data-warehouse/migrate-using-upload-file)). Source and target are both T-SQL, so this is narrowing a dialect, not changing language.
- Reporting: the summary shows "the count of migrated objects and the objects that need to be fixed". For migrated objects "the State column indicates if the Migration Assistant adjusted the object's metadata" and Details describes the adjustment. A failed object opens as a query showing "the adjustments that were made to it as automatic comments added to the T-SQL code" (same page).
- Failure ordering: failed scripts are split into primary objects and dependent objects. "Dependent objects won't be migrated until their primary objects are fixed". Primary objects are "sorted by priority" by number of dependants (Migration Assistant page).
- The model: "To use Copilot for AI-powered assistance in fixing the errors, select **Fix query errors** in the **Suggested action** section. Copilot updates the script with suggestions. Mistakes can happen as Copilot uses AI, so verify code suggestions". Then "Select **Run** to validate and create the object" (upload-a-file page). One call per failed object, started by a person, checked by the target accepting the `CREATE`.
- The manual methods page lists Data Factory, SQL scripts, SQL database projects and dbt. Scripts and projects can "flag" or "assess unsupported T-SQL syntax in stored procedures, functions, and views" ([migration methods](https://learn.microsoft.com/en-us/fabric/data-warehouse/migration-sql-server-methods)). Nothing on these pages converts T-SQL procedures to Spark notebooks.

## Published systems outside the vendors

No published paper or first-party engineering post was found that describes a multi-agent system converting T-SQL or PL/SQL stored procedures to PySpark. Searches returned only consultancy and vendor pages (LTM, Xebia, ACL Digital, an AWS Marketplace listing). Those are marketing, give no architecture that can be checked, and are not used as evidence here.

Three published systems are close enough to learn from.

### CrackSQL: rules plus LLM for SQL dialect translation

- A SIGMOD 2025 paper and SIGMOD 2026 demo with open code ([arXiv 2504.00882](https://arxiv.org/abs/2504.00882), [repository](https://github.com/weAIDB/CrackSQL)).
- The abstract states the problem with each pure approach: rule-based systems "involve high maintenance effort" and an LLM "generates non-existent functions". CrackSQL is "the first hybrid SQL dialect translation system that combines rule and LLM-based methods", "segmenting lengthy complex SQL via functionality-based query processing" with "an adaptive local-to-global translation strategy".
- The repository offers three modes: rule-only (SQLGlot rules, 24 dialects), LLM-direct, and rule plus LLM (3 dialects, using an ANTLR parser and a dialect specification).
- Its README reports, on the authors' own benchmark, result-equivalence accuracy for PostgreSQL to MySQL of 70.97% for SQLGlot alone, 61.29% for GPT-4o alone and 74.19% for CrackSQL, and for MySQL to PostgreSQL 60.32%, 44.44% and 79.37%. These are the authors' figures and were not reproduced. The direction they point in is that the hybrid beats either alone and that an unassisted model can do worse than rules.
- It is SQL to SQL only.

### TransAgent: multi-agent code translation with execution alignment

- Accepted at FSE 2026 ([arXiv 2409.19894](https://arxiv.org/abs/2409.19894), body read at [v5](https://arxiv.org/html/2409.19894v5)).
- Four agents in a fixed order with loops: an Initial Code Translator, a Syntax Error Fixer that "iteratively addresses the syntax errors in the target program based on compilation or interpreting error messages", a Code Aligner that "divides the source program into blocks based on the control flow" and maps each to the target, and a Semantic Error Fixer that "localizes the suspicious block in the target program, which exhibits different runtime behaviors".
- The agents do not choose their own next step. By this project's definitions it is a pipeline of LLM steps with bounded loops, named as agents.
- Deterministic tools carry the judgement: compilers for syntax, a control-flow graph tool for splitting, inserted log statements for comparing values block by block, and test execution for equivalence.
- Tests are made by asking the model for inputs and running the source program to get expected outputs.
- The paper reports that the syntax fixer gives the largest gain in its Python to Java ablation and the semantic fixer a smaller one. The cheap oracle did most of the work.
- The ablation figures were read from the paper body (v5): on Python to Java, accuracy rises from 49.5% to 82.4% with the syntax fixer and to 89.5% with the semantic fixer.
- It translates between Python, Java and C++ at function scale, not SQL.

### Microsoft Legacy Modernization Agents: COBOL to Java or C#

- An open-source Microsoft sample, actively maintained ([repository](https://github.com/Azure-Samples/Legacy-Modernization-Agents), last pushed 2026-10-11). All points below are from its README.
- Parsing comes first and uses no model. `rekt-full` "parses the COBOL with REKT into the REKT Neo4j graph" and "No model is called". The conversion diagram starts with "Program facts from the REKT parse, copybooks and call contracts (deterministic, no model)".
- The agents are named roles called in a fixed order by a migration process: `CobolAnalyzerAgent`, `DependencyMapperAgent`, a Java or C# converter agent ("chunked for large programs"), and `BusinessLogicExtractorAgent` for documentation. The README's own data-flow list is numbered steps. No agent chooses the order.
- Gates are deterministic. An "output guard" checks each answer is complete code. A "compile gate" runs `dotnet build`. A `CompileRepairAgent` "fixes file by file, up to `CompileGate.MaxRepairRounds`, undoes rounds that make it worse". A "conversion parity check" is described as a "deterministic check that generated code represents the COBOL it came from, with per-axis coverage and a configurable threshold". It reports and can stop the run "but does not repair".
- Job control language is handled with no model at all: "read by a built-in deterministic parser, and the jobs are generated from it without a model".

### Google's internal migrations

- "Migrating Code At Scale With LLMs At Google" ([arXiv 2504.09691](https://arxiv.org/abs/2504.09691)). Only the abstract was read. It describes "a novel automated algorithm that uses change location discovery and a Large Language Model (LLM)", and reports that across 39 migrations 74.45% of code changes were LLM-generated. The abstract calls it an "automated, LLM-assisted workflow". Deterministic discovery of where to change, then a model to make the change, is the same division as the vendors'.

## What this suggests for the tickets that wait on it

These are inferences from the findings above, offered as input. The decisions belong to the tickets.

**For "What representation does the core work on?" (#11)**

- No surveyed tool demonstrates a single IR serving several targets. The claim that the core can stay unchanged when Snowflake SQL is added as a second target has no precedent among these products and needs its own evidence.
- Every surveyed tree-based engine targets SQL, so its tree can stay close to SQL syntax. A DataFrame API target is a different shape of output. The only tools that produce Python from T-SQL do it by wrapping SQL strings (BladeBridge by template, Switch by prompt) or by handing the whole artefact to a model (Databricks agentic converter). None of them shows what representation makes deterministic DataFrame generation possible.
- Google's translator and SnowConvert both depend on resolved names and table shapes (metadata DDL, symbol table). Morpheus explicitly does not type-check and says so as a limitation.

**For "Which autonomy level does each component get?" (#14)**

- The repeated design is: deterministic conversion for the bulk, an LLM step for the coded residue, a bounded repair loop driven by a deterministic check, and a label on everything the model wrote. That matches `CONTEXT.md`'s flagged fragment.
- Systems that call their parts "agents" (TransAgent, Legacy Modernization Agents, Switch's "orchestrator") turn out, on reading, to run them in a fixed order. The owner's hypothesis of an orchestrator agent choosing steps has no support in any system whose internals could be read.
- The places where a real agent loop is documented are narrow: per-artefact convert, validate and retry (Databricks, Snowflake), and test-case generation (Snowflake). The other place is outside the tool, where a general coding agent drives the deterministic service through an API and a skill (AWS, Google, Snowflake).
- AWS's design gives a concrete trigger for the LLM step: a specific rule-failure code on a specific statement. That is easier to test and to cache than "the model looks at the file".

**For other tickets**

- **Conversion report (#9).** Snowflake's scheme is the most complete model found: a code per issue, a category that separates "not converted" from "converted but behaves differently", a severity based on effort to fix, a location, and a marker that stops unreviewed code from compiling. AWS adds a distinct code for model-written statements. Microsoft adds ordering of failures by number of dependants.
- **Reconciliation (#13).** Snowflake's Seed, Capture, Validate pipeline is the only documented implementation of what `CONTEXT.md` calls reconciliation: baseline from the source, run on an isolated copy, compare result sets, output parameters and table changes, with test inputs from query logs or synthesised data.
- **Constructs with no PySpark equivalent (#10).** Switch's shared prompt is a first-party list of Databricks' own recommended treatments for temp tables, transactions, cursors, `UPDATE ... FROM`, `DELETE` with joins and parameters. AWS extension packs and Google's `bqutil` UDFs show the other option, a target-side emulation library.
- **Reviewer fixes returning to the tool (#16).** Every vendor has this channel: BladeBridge override files, Switch prompt files, Databricks skills, Snowflake's rule engine with "search, apply, extract, propagate", Google's configuration YAML.
- **Scope and positioning (the map, #1).** Databricks' own agentic code converter went to Beta in July 2026, and its documentation as of September 2026 lists T-SQL as a source and DataFrame API notebooks as a target, inside the target platform, with limits of 1,000 lines per script and 300 files per batch. That is a direct overlap with v1. It is LLM-produced, and how it treats stored procedures is undocumented, so a deterministic, reported and reconciled conversion would still differ from it. The overlap should be weighed before v1 scope is fixed.
